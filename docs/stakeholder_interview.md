# 담당자 인터뷰 — 카테고리별 질문 (단일 원본)

- 인터뷰 목적 = PRD 구체화. 답은 `$prd` 가 PRD 6절(업무 규칙 B)·9절(가정 A) ID 로 옮긴다. PRD 의 빈칸을 채우지 않는 질문은 보내지 않는다.
- 업무 사실만 묻는다. 해법 단어(자동화·AI·대시보드·모델)와 구현 용어는 쓰지 않는다.
- `$kickoff` 가 TASK 3절 질문 표를 만든다. 보내는 일(묶음·순서·시점)은 이 문서대로 사람이 한다.
- `담당자 확인: 필요` 질문은 A_core·C_verify 만 만든다. B_web 의 화면 질문(F)은 사람이 대신 묻는다.

## 1. 카테고리 표

| 코드 | 카테고리(사용자 예시 매핑) | 개수 | 캐낼 것 | 답할 수 있는 예문 | 보내면 안 되는 예 |
|---|---|---|---|---|---|
| R | README 가 "담당자에게 확인" 한 항목 | 전부 | README 가 일부러 비워 둔 값·형식 | "아침 보고에 꼭 들어가야 하는 항목은요?" | — |
| A | 맥락·현재 방식(기존방식) | 0~2 | 지금 손으로 하는 순서, 최근에 고친 사례 속 규칙 | "최근에 결과를 다시 고친 적이 있나요? 무엇 때문에요?"(첫 질문 고정 — 세 리허설에서 첫 답에 규칙 5~6개) | "하루 늦으면 손실이 얼마나?" |
| B | 판정·계산 규칙(세부요구사항) | 0~3 | 경계값 포함 여부, 기준이 없는 경우, 계산 순서 | "하한과 딱 같으면 통과인가요? 하한이 없는 제품은요?" | "lift 분모를 all_lots 열로 잡아도 되나요?"(구현 용어) |
| C | 세는 대상·제외·중복 | 0~3 | 무엇을 세고 무엇을 빼나, 중복이면 무엇을 남기나 | "같은 웨이퍼가 두 번 있으면 어느 것을 쓰세요? 재테스트 표시가 없는데도요?" | "01 과 LT260102-01 은 같은 웨이퍼인가요?"(표기 → 데이터로 결정) |
| D | 숨은 규칙 찾기(조합 조건·이름 겹침·하루 경계) | 0~3(고정 2) | 통과해도 따로 보는 조합, 같은 이름이 겹치는 범위, 자정 넘김 | "기준을 통과해도 따로 보는 lot 이 있나요? 몇 개부터요?" / "같은 장비 이름이 다른 팹·라인에도 있나요?" | "eqp_id 공백·대소문자 차이는 같은 장비인가요?"(IT) |
| E | 결측·오류 처리·표시(서비스 시 예상 에러) | 0~2 | 빈 값·안 맞는 값을 넣나 빼나, 어디에 표시하나 | "수량이 안 맞거나 빈 웨이퍼는 판정에 넣나요, 따로 적나요?" | "같은 시각에 결과 둘이면 어느 걸 믿나요?"(데이터 결정) |
| F | 출력·화면·우선순위 | 0~2 | 먼저 보는 것, 절대 나가면 안 되는 결과 | "화면을 열면 제일 먼저 보는 게 뭔가요?" / "절대 나가면 안 되는 결과는?" | "리페어 전후를 나란히 보여주면 될까요?"(해법 제안) |

- 사용자 예시 매핑: 기존방식 → A · 세부요구사항 → B · 서비스 시 예상 에러 → E · 기술구현 → 카테고리가 아니라 2절 제외 목록.
- 개수: 행마다 0~3, README 가 답하면 0(개수 채우기 금지). 총 개수는 고정하지 않는다. R 행과 README 가 답한 것은 세지 않는다.
- D 고정 행 2개 = 조합 조건("통과해도 따로 보는 것") · 이름 겹침("다른 팹·라인에도 같은 이름"). 하루 경계(자정 넘김)는 EDA 단서가 있을 때 더한다.
- 자동으로 들어오는 후보 2가지:
  - `$kickoff` 가 README '담당자에게 확인' 문구를 R 행으로 복사한다.
  - `eda_bootstrap` 요약 끝 `## 담당자 질문 후보` → C·D 행 후보(단위 혼재·완전 중복 행·시각 형식 혼재·자정 넘김·식별자+범주 열 조합).

## 2. 제외 목록 (기술구현 — 질문하지 않는다)

| 제외 | 예 |
|---|---|
| 표기 | 대소문자·공백·접두어·날짜 표기 차이가 같은 것인지 |
| 식별자 | 키 조합·ID 형식, 어느 열을 합쳐야 유일한지 |
| IT | 인코딩·구분자·파일 경로·시스템 출처 |
| 정답 자료 | "정답 목록·엑셀을 보내 주세요"(성공 기준은 규칙으로 묻는다) |
| 화면 배치 | 표·그래프 배치, 색, 나란히 보기(F 는 '무엇을 먼저 보나'만) |

- 제외 항목은 pending 에 `담당자 확인: 불필요 — 데이터 결정` 으로 적고 `담당자 질문:` 줄을 두지 않는다(AGENTS 5절).
- 전송 전 3줄 검사: 엑셀로 할 때 내가 정할 일인가 / README 에 있나 / 이미 받은 답인가. 하나라도 '예'면 보내지 않는다.

## 3. 전송 규칙

| 묶음 | 내용 | 때 |
|---|---|---|
| 1 | R + A + B + C 에서 3~4개 | `$kickoff` 직후 |
| 2 | D + E + F + 1차 답이 빠진 코드에서 3~4개 | 1차 답을 TASK 3절에 옮긴 뒤 |
| 3 | pending `담당자 확인: 필요` 항목 묶음(있을 때만) | CP 때 |

- PRD 검토 요청(4절)은 묶음 2 답을 TASK 3절에 옮기고 `$prd` 초안을 사람이 검토한 뒤 1회 보낸다.
- 묶음은 3~4개씩 2~3회. 첫 답 모양을 보고 사람이 크기를 조정한다. 담당자 AI 는 묶음에서 하나만 답하는 경향이 있다.
- 한 코드에 한 주제. 무응답 코드는 다음 묶음에 한 번 더 넣는다.
- 질문 코드 = 카테고리 + 번호(`A1`·`B2`). 메신저 `B2.` ↔ 답 `답변 B2: …`(T1 에 붙임) ↔ TASK 3절 같은 코드 행.
- TASK 3절 열: `코드 | 질문 | 답 요지 | 시각 | 결과(PRD ID·Dnn)`.
- '모름'·'담당 아님' → TASK 3 답 요지에 그대로, `$prd` 가 PRD 9 가정으로(틀리면 깨지는 것·안전한 쪽). 같은 주제 재질문 금지.
- pending `필요` 항목은 생길 때마다 보내지 않는다. 카테고리별로 모아 CP 때 묶어 보낸다(질문 코드 = 결정 ID, 예 `D07.`). 답은 그 항목 메모 또는 창에 `답변 D07: …`.
- 답이 PRD 승인 뒤의 새 요구면 T1 에 `요구사항 갱신:`(`docs/prompts.md` 7) → `$prd 갱신`.

메신저 틀:
```
업무 확인 질문 [N]개입니다. 코드별로 답해 주세요(예: B2: …). 모르시면 "모름" 이라고만 적어 주세요.
A1. 최근에 결과를 다시 고친 적이 있나요? 무엇 때문에요? (지금 방식에서 자주 틀리는 곳을 알려고요)
B1. [질문] ([무엇을 정하려고요])
C1. [질문] ([무엇을 정하려고요])
```

## 4. PRD 검토 요청 5줄 (담당자에게 · DECISIONS 0 에 시각 · 회신 전 코드 금지)

`$prd` 가 초안을 내고 사람이 PRD.md 를 읽고 고친 뒤 보낸다. 내용은 PRD 3·5·6 의 요약이다.

```
제가 이해한 내용입니다. 맞나요? 다른 점이 있으면 번호로 알려 주세요.
1. 만들 것: (PRD 3 안 — 한 줄)
2. 안 만들 것: (PRD 3 밖 — 대신 쓰는 것)
3. 꼭 되어야 하는 것: (PRD 5 MUST 2~3개, 업무 말로)
4. 판정·계산 규칙: (PRD 6 핵심 1~2개, 경계 포함 — 예 "하한과 같으면 통과")
5. 빼는 것·단위·하루 경계: (PRD 6 제외·단위·시간대)
```

- 보낸 시각은 DECISIONS 0 `PRD 송부:`, 회신은 `담당자 회신: HH:MM "원문"` 으로 고치지 않고 남긴다. 회신의 다른 점은 PRD 본문에 반영한 뒤 사람이 "PRD 승인"(v1).
- 승인 뒤 바뀐 것은 `요구사항 갱신:` → `$prd 갱신`: 내용은 PRD 10절, DECISIONS 0 에는 시각만.
- 성공 기준은 규칙·형식으로 적는다. 정답 목록·현재값을 요구하지 않는다.

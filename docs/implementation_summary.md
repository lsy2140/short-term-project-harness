# 최종 구현 종합정리 (작업 마무리 · 모든 문장에 증거 좌표)

무엇을 왜 어떻게 만들었고, 어떻게 검증했고, 어디서 틀릴 수 있는지를 `out/report/implementation_summary.md` 한 문서로 모은다.
정리한 내용과 실제 구현이 다르면 구현을 기준으로 고친다.

| 언제 | 누가(창) | 무엇을 |
|---|---|---|
| 매 task 끝 | 각 에이전트 | 아래 '작업 중 기록 습관' 한 줄씩 |
| CP2 통합 때 | T3 `$verify-agent summary`(FROZEN 전 = 핵심 3개만) | 맨 위 '핵심 3개' 초안 |
| 동결 선언 뒤(CP3) | T3 `$verify-agent summary` | 이 지침대로 나머지 전부 + 핵심 3개 숫자·좌표 갱신 |

## 핵심 3개 (맨 위 · CP2 통합 때 초안 → CP3 에서 숫자만 갱신)
CP3 는 제출 카드와 겹친다. 그래서 문장은 CP2 에 써 두고, 동결 선언 뒤에는 숫자·좌표만 바꾼다.
- ① 작동 원리: "___ 를 받아 ___ 규칙(B01~B__)으로 ___ 를 정하고 ___ 를 낸다. 중심 함수는 ___(파일:함수)다.
  규칙마다 지킨 근거는 '규칙 ↔ 코드 ↔ 검증' 표에 있다."
- ② 가장 위험한 실패: "___ 입력에서 틀린다. 그러면 ___가 틀어진다. DECISIONS.md 5번에 적었고, 고치려면 ___가 필요하다."
- ③ 바꾼 것 1개와 이유: "처음에는 ___ 였고 ___ 로 바꿨다. ___ 때문이다(출처: 답변 B2·D07·test_xxx).
  버린 쪽은 ___ 가 문제였고, 바꾼 뒤 ___ 로 다시 검증했다(파일:줄)."
- 문서 어디든 "바꿨다"·"고쳤다" 라고 적었으면 그 일의 전/후·이유·검증이 ③ 또는 결함 사례 카드에 있어야 한다.

## 기준 세 가지
1. **설명은 실제 구현과 대조된다.** 작업 중에는 산출물과 함께 프롬프트·도구 설정·AI 대화·검증 실행 기록이 남는다.
   설명은 그 기록과, 판단의 근거가 된 코드 위치에 비춰 확인된다.
   그래서 모든 문장에 코드 위치(파일:줄·함수)나 실행 기록을 붙이고, 그 줄을 다시 열어 문장과 맞는지 대조한다.
   기록에 없는 것은 쓰지 않는다.
2. **중심은 두 가지다. "이 부분을 왜 이렇게 만들었나"와 "장애가 나면 어떻게 되나".**
   둘은 각각 표(부분별 설계 이유 · 장애 대응표)로 빠짐없이 정리한다.
   어느 코드 줄을 짚어도 이유와 실패 시 동작을 말할 수 있어야 한다.
3. 작동 원리와 실패 가능성을 내 말로 쓴다. 검증·인지 축이 가장 낮게 나오기 쉽다. 전문 용어 대신 입력 → 규칙 → 출력으로 쓰고, 한계는 숨기지 않는다.

## 작업 중 기록 습관 (종합정리의 재료 · 한 줄이면 충분)
| 습관 | 어디에 남기나 | 종합정리에서 쓰는 곳 |
|---|---|---|
| 단계가 끝날 때마다 "왜 이렇게 했나" 한 줄. 기억에 기대지 않는다 | `out/debug/NN_*/note.md` · `work/agents/<이름>.md` ⑤(단일 세션은 DECISIONS 1) · 코드 `# 결정:` | 부분별 설계 이유 · F |
| 한계는 약점 → 위험 → 다음 검증 순서로 적는다 | DECISIONS 5번 | 장애 대응표 · G·H |
| 대체값·추정값·폴백은 플래그·사유 열로 실제 결과와 구분하고 건수를 센다 | 출력 상태 열 · metadata/audit | 대체값·추정값·제외 표 |
| 검증은 눈이 아니라 실행 기록으로 남긴다 | `green.txt`·`red.txt`·`verify.json` · DECISIONS 6번 | G |
| 겉보기(README 문구·흔한 가정)와 실제 구현이 다른 곳을 그때그때 적는다 | DECISIONS 1 · `# 결정:` | 오해하기 쉬운 지점 |
| 계획·방법을 바꾸면 그때 전/후·이유·출처 한 줄("바꿨다" 고 쓸 곳마다) | work 파일 ⑤ 'NN 끝' 행(단일 세션은 DECISIONS 1) | 핵심 3개 ③ · E 핵심 알고리즘 |
| 결함은 증상·발견 경로·맡긴 것/직접 한 것·검증 명령까지 한 줄 | DECISIONS 4번 | 결함 사례 카드 · D 항목 |

줄이려면 글자가 아니라 문장 수를 줄인다(띄어쓰기·조사를 빼서 줄이지 않는다). 작업 중에는 한 줄씩만 남기고, 문장으로 펴는 일은 동결 선언 뒤 C_verify 가 한다.

## 문서 모양
```
# 최종 구현 종합정리 — <과제 이름>
한 문장: (TASK.md 한 문장 그대로)
## 핵심 3개                       ← 맨 위
## 오해하기 쉬운 지점
## 부분별 설계 이유               ← 표, 8~15행
## 규칙 ↔ 코드 ↔ 검증             ← 표, PRD 6 규칙마다 1행
## 데이터·모듈 흐름               ← 표, 단계마다 1행
## 장애 대응표                    ← 표, 기본 행 전부
## 대체값·추정값·제외             ← 표
## 결함 사례 카드                 ← DECISIONS 4 행마다 1장
## A. 개요 … ## H. 한계·다음 할 일  ← 정리 항목 번호 그대로, 빠짐없이
## 설명이 막힌 항목
## 근거 없음 목록                 ← 기록에서 숫자·좌표를 못 찾은 것
```

## 골격
### 골격 1 — 결정형 (사실 → 결정 → 근거 → 한계)
```
사실  "README·담당자는 X라고만 정했다."
결정  "그래서 Y로 정했다. 대안 Z는 ~ 때문에 버렸다."
근거  "test_xxx 3개와 preflight로 확인했다(파일:줄)."
한계  "W인 입력에서는 틀린다. 그러면 ~가 틀어진다. ~를 확인하고 테스트를 더한다(DECISIONS.md 5번)."
```

### 골격 2 — 약점형 (지목 → 파급 → 계획)
위험·장애·가장 약한 곳은 세 단계로 쓴다.
```
지목  "약점은 <파일>의 <함수/규칙>이 <조건> 입력을 처리하는 방식이다."          ← 구체적 좌표
파급  "이 경우 <결과물>이 <어떻게> 틀리고, <누가> <어떤 결정>을 잘못하게 된다."  ← 왜 위험한가
계획  "<테스트/확인>으로 검증하고 <수정>한다. 지금은 DECISIONS.md 5번에 기록했다." ← 검증·개선
```

### 골격 3 — 확인하지 않은 것
```
"확인하지 않았다. 위험: ___. 확인하려면 ___(명령·테스트·담당자 확인)."
```
추측으로 채우지 않는다. 아는 척보다 "확인하지 않음 + 위험 + 확인 방법"이 낫다.

금지: 근거 없는 "테스트했다" / AI·시간 탓 / 기록과 다른 숫자. 산출물과 어긋나는 내용, 일반론, AI 말투는 뺀다. 파일명·함수명·테스트명·숫자를 넣고 내 말투로 쓴다.

### 오해하기 쉬운 지점 (겉보기와 실제 구현이 다른 곳)
겉보기나 흔한 가정이 실제 구현과 다르면, 가정에 맞춰 설명하지 않고 실제 구현을 먼저 적는다.
| 겉보기·흔한 가정 | 실제 구현 | 좌표 | 그렇게 한 이유 |
|---|---|---|---|
| 예: README "기준 초과면 알람" | 같은 값도 알람(`>=`) | `rules.py:42` · `test_threshold_equal_included` | 담당자 답 B2 |

### 부분별 설계 이유 (핵심 코드 지점마다 1행 · 8~15행)
대상: 진입점, 규칙 함수 각각, 임계값·상수, 정렬·tie-break, 제외·필터, 대체값 처리, 출력 쓰기, (웹) 요청 검증·응답에서 뺀 필드.
| 코드 위치(파일:줄·함수) | 무엇을 | 왜 이렇게 | 버린 대안과 이유 | 틀리면 생기는 일 | 근거(테스트·기록) |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

### 규칙 ↔ 코드 ↔ 검증 (PRD 6 의 B 규칙마다 1행 · 빠진 규칙 0)
규칙이 어디서 지켜지고 무엇으로 확인됐는지 한 줄에 잇는다. 테스트가 없으면 상태 `NOT_RUN`, 눈으로만 봤으면 `HUMAN_CHECK`.
| 규칙 ID(PRD B) | 규칙 한 줄 | 지키는 코드(파일:함수) | 지킴을 보인 테스트 | 발동 건수·재계산 결과 | 상태 |
|---|---|---|---|---|---|
| 예: B02 | 기준과 같은 값도 알람 | `rules.py:42 is_alert()` | `test_threshold_equal_included` | 발동 12행 · 재계산 일치(`stages.md` 02절) | PASS |

### 데이터·모듈 흐름 (PLAN 4 단계마다 1행 · 입력 파일부터 출력·화면까지)
PLAN 4 task 표·4-2 연결 표와 `python3 scripts/docmap.py` 지도에서 옮긴다. 담당이 바뀌는 곳은 연결 표 번호를 같이 적는다.
| 단계 | 들어오는 것 | 모듈(파일:함수) | 나가는 것(파일·열) | 관리 주체(A/B/C·사람) | 저장 위치 | 검증 방법 |
|---|---|---|---|---|---|---|
| 예: 02 판정 | `data/raw.csv` 5열 | `core/judge.py:20 apply()` | 판정·제외 사유 열 | A 구현 · C 재계산 · 사람 D03 결정 | 메모리 → `out/result.csv` | `test_judge_*` 6개 · `stages.md` 02절 |

## 정리 항목 (관점별 · 전부 채운다 · 해당 없으면 "해당 없음 — 이유" 한 줄)

### A. 개요
1. 한 문장 목표, 결과물의 사용자, 그 사용자가 바꾸는 결정
2. 실행 명령 한 줄과 입력 → 출력 흐름(파일 이름·행 수)
3. 작동 원리 3줄: 입력 → 규칙 → 출력, 전문 용어 없이
4. 제출물 목록과 파일별 역할(README 가 정한 이름·형식 그대로인지)
5. 성공 기준을 숫자로(측정 방법, PRD 2)

### B. 의도 — 목표·제약
6. 반드시 지킬 조건과 조정 가능한 조건의 구분, 섞으면 생기는 문제
7. 상충 조건과 어느 쪽을 택했는지, 그 이유
8. README 에 없어 가정한 것과 틀리면 깨지는 것(PRD 9)
9. 하지 않기로 한 것과 이유(PRD 3 밖)

### C. 담당자 확인·결정
10. 담당자에게 물은 것과 답이 설계를 바꾼 곳(질문 코드 `B2` → TASK 3절 결과 열의 PRD ID → 바뀐 코드 위치)
11. PRD 요지(3 범위·5 기능·6 규칙)·승인 시각·변경 이력(PRD 10절 + DECISIONS 0 확인 기록)
12. 사람이 고른 결정 전부(`decisions/answers.md` 의 D번호 · 고른 후보 · 이유 · 담당자 답)
13. 담당자 답이 없거나 애매했던 곳과 처리 방법

### D. AI 활용 — Codex 위임과 검증
14. Codex 에 맡긴 것과 직접 한 것의 경계, 그렇게 나눈 이유(PLAN 8 · DECISIONS 1 결정자 열)
15. 목표·제약을 전달한 주요 위임 3개의 요지(목표·범위·금지·완료 조건)와 효과
16. Codex 출력을 믿지 않은 지점과 검증 방법
17. Codex 가 틀린 사례 하나와 발견·수정 과정(결함 사례 카드 1장 요약, DECISIONS 4번)
18. 사용한 도구 설정: 승인 모드·쓴 스킬(`$kickoff`·`$prd`·`$plan`·`$rule-loop`·`$web-ui`·`$verify-agent`)
    ·창 구성(A_core·B_web·C_verify·T4 심사)과 소유권(`work/README.md`)·연결 표(PLAN 4-2)
19. 토큰·시간을 아끼려고 한 것
20. 저장하지 않기로 한 데이터 또는 출력에서 뺀 열과 이유
21. 모델(또는 담당자 AI)이 준 값이 없거나 틀렸을 때 시스템이 하는 일

### E. 기술 — 구조·흐름·보안
22. 핵심 알고리즘: 입력 → 규칙 → 출력 3줄 · 바꾼 것 전/후 · 왜(출처: 답변 코드·Dnn·테스트) · 버린 대안 1개
23. 코드 구조: 파일별 역할(`python3 scripts/docmap.py` 지도), 순수 함수(`solve`)와 입출력 분리, 단계 = 모듈 = 테스트 파일('데이터·모듈 흐름' 표)
24. 같은 입력에 같은 출력을 보장하는 방법(정렬·tie-break·반올림)
25. 결측·중복·경계값·시간대 처리와 코드 위치
26. 예외·실패 시 동작과 사용자가 아는 방법(장애 대응표에서 가장 위험한 2행 요약)
27. 비밀정보·개인정보 처리, 화면·출력에서 뺀 내부 필드
28. 데이터가 10배일 때 먼저 무너지는 곳
29. 더 단순한 대안을 쓰지 않은 이유

### F. 단계별 구현 (PLAN 4번 단계마다)
30. 단계 블록: 역할 1줄 · 작동 원리 3줄 · 구현 위치(파일:줄·함수) · 왜 이 방법(한 줄) · 결과 숫자(출처) · 테스트 이름 · 상태
31. 규칙 전체 요약: '규칙 ↔ 코드 ↔ 검증' 표의 PASS·NOT_RUN·HUMAN_CHECK 수, 발동 0건 규칙(PLAN 4번)
32. 합계 보존: 입력 건수 = 통과 + 제외(사유별) 숫자와 확인 방법
33. 단계 설명(`out/report/stages.md`, C_verify)에서 확인한 것과 고친 것

### G. 검증·인지
34. 규칙별 검증 방법: '규칙 ↔ 코드 ↔ 검증' 표 참조 — 테스트·재계산·HUMAN_CHECK 중 무엇으로 봤나, 표에 없는 규칙 0개
35. 테스트 구성과 결과(과제 테스트만 — 정상·업무 규칙·경계값·실패 경로·계약이 각각 몇 개, 하네스 도구 테스트 제외)
36. 먼저 FAIL 을 본 테스트와 그때 실패 내용
37. 검증 실행 기록: 명령·시각·결과(`green.txt`·DECISIONS 6번), 눈으로만 확인한 것과 그 이유
38. 핵심 숫자를 다른 방법으로 다시 계산한 결과
39. 사람이 직접 확인한 것(HUMAN_CHECK)과 결과
40. 담당자가 "이 숫자는 틀렸다"고 할 때 확인 순서
41. 가장 약한 부분과 틀리는 입력 하나(골격 2)
42. 설명하기 어려웠던 코드 줄과 쉬운 말 설명

### H. 한계·다음 할 일
44. 못 한 것과 이유(PLAN 9 · HANDOFF 5)
45. 실서비스 한계 3개: 동시 요청 · 규모(입력 10배·사용자 수) · 권한/보안(로그인·입력 검증)

## 용어 → 내 말 (정리에는 오른쪽 말로 쓴다)
| 용어 | 내 말로 |
|---|---|
| hard constraint / 위생 요건 | **빼는 것.** 후보에서 아예 제외한다 |
| soft ranking / 점수 | **줄 세우는 것.** 순서만 정한다, 빠지지는 않는다 |
| tie-break | 점수가 같을 때 누가 먼저 나올지 정한 규칙 |
| 결정론적 / 재현성 | 두 번 돌려도 같다 |
| 견고성 / robustness | 이상한 게 들어와도 안 터진다 |
| fallback | 원래 방법이 안 될 때 쓰는 대비책, 썼다는 표시를 남긴다 |
| 경계값 / edge case | 딱 걸치는 값(임계값과 같음, ±1) |
| sentinel / 표시용 값 | "값 없음"을 뜻하려고 넣은 가짜 숫자(-9999 등) |
| leakage / 누수 | 아직 안 일어난 미래 정보를 몰래 쓰는 것 |
| 멱등성 | 같은 요청을 두 번 받아도 한 번 받은 것과 결과가 같다(중복 생성 없음) |
| 동시 요청 / 경쟁 조건(race condition) | 두 요청이 거의 같은 때 같은 데이터를 바꿔서, 늦게 끝난 쪽이 앞 결과를 덮거나 반만 반영되는 것 |
| 잠금(lock) | 한 번에 한 요청만 쓰게 막는 표시. 다른 요청은 기다리거나 '처리 중' 을 받는다 |
| 가드레일 | 절대 나가면 안 되는 결과를 코드로 막은 것 |
| TDD / 먼저 FAIL | 확인할 문장을 먼저 정하고, 안 되는 걸 보고, 되게 만든다 |

# 최종 구현 종합정리 (작업 마무리 · 모든 문장에 증거 좌표)

무엇을 왜 어떻게 만들었고, 어떻게 검증했고, 어디서 틀릴 수 있는지를 한 문서로 모은다. 동결 구간(144분~)에 보고서 세션에서 `$implementation-summary` 가 이 지침대로 `out/report/implementation_summary.md` 를 만든다. 정리한 내용과 실제 구현이 다르면 구현을 기준으로 고친다.

## 기준 세 가지
1. **설명은 실제 구현과 대조된다.** 작업 중에는 산출물과 함께 프롬프트·도구 설정·AI 대화·검증 실행 기록이 남는다. 설명은 그 기록과, 판단의 근거가 된 코드 위치에 비춰 확인된다. 그래서 모든 문장에 코드 위치(파일:줄·함수)나 실행 기록을 붙이고, 그 줄을 다시 열어 문장과 맞는지 대조한다. 기록에 없는 것은 쓰지 않는다.
2. **중심은 두 가지다. "이 부분을 왜 이렇게 만들었나"와 "장애가 나면 어떻게 되나".** 둘은 각각 표(부분별 설계 이유 · 장애 대응표)로 빠짐없이 정리한다. 어느 코드 줄을 짚어도 이유와 실패 시 동작을 말할 수 있어야 한다.
3. **작동 원리와 실패 가능성을 내 말로 쓴다.** 검증·인지 축이 가장 낮게 나오기 쉽다. 전문 용어 대신 입력 → 규칙 → 출력으로 쓰고, 한계는 숨기지 않는다.

## 작업 중 기록 습관 (종합정리의 재료 · 한 줄이면 충분)
| 습관 | 어디에 남기나 | 종합정리에서 쓰는 곳 |
|---|---|---|
| 단계가 끝날 때마다 "왜 이렇게 했나" 한 줄. 기억에 기대지 않는다 | `out/debug/NN_*/note.md` · DECISIONS 1번 · 코드 `# 결정:` | 부분별 설계 이유 · F |
| 한계는 약점 → 위험 → 다음 검증 순서로 적는다 | DECISIONS 5번 | 장애 대응표 · G·H |
| 대체값·추정값·폴백은 플래그·사유 열로 실제 결과와 구분하고 건수를 센다 | 출력 상태 열 · metadata/audit (AGENTS.md 4절) | 대체값·추정값·제외 표 |
| 검증은 눈이 아니라 실행 기록으로 남긴다 | `green.txt`·`red.txt`·`verify.json` · DECISIONS 6번 | G |
| 겉보기(README 문구·흔한 가정)와 실제 구현이 다른 곳을 그때그때 적는다 | DECISIONS 2번 · `# 결정:` | 오해하기 쉬운 지점 |

긴 글은 구현 시간을 뺏는다. 작업 중에는 한 줄씩만 남기고, 문장으로 펴는 일은 보고서 세션이 한다.

## 문서 모양
```
# 최종 구현 종합정리 — <과제 이름>
한 문장: (TASK.md 한 문장 그대로)
## 핵심 3개                       ← 맨 위
## 오해하기 쉬운 지점
## 부분별 설계 이유               ← 표, 8~15행
## 장애 대응표                    ← 표, 기본 행 전부
## 대체값·추정값·제외             ← 표
## A. 개요 … ## H. 한계·다음 할 일  ← 정리 항목 번호 그대로, 빠짐없이
## 설명이 막힌 항목
## 근거 없음 목록                 ← 기록에서 숫자·좌표를 못 찾은 것
```

## 골격
### 골격 1 — 결정형 (사실 → 결정 → 근거 → 한계)
```
사실  "README·담당자는 X라고만 정했다."
결정  "그래서 Y로 정했다. 대안 Z는 ~ 때문에 버렸다."
근거  "test_xxx 3개와 preflight로 확인했다(파일:줄)."
한계  "W인 입력에서는 틀린다. 그러면 ~가 틀어진다. ~를 확인하고 테스트를 더한다(DECISIONS.md 5번)."
```

### 골격 2 — 약점형 (지목 → 파급 → 계획)
위험·장애·가장 약한 곳은 세 단계로 쓴다.
```
지목  "약점은 <파일>의 <함수/규칙>이 <조건> 입력을 처리하는 방식이다."          ← 구체적 좌표
파급  "이 경우 <결과물>이 <어떻게> 틀리고, <누가> <어떤 결정>을 잘못하게 된다."  ← 왜 위험한가
계획  "<테스트/확인>으로 검증하고 <수정>한다. 지금은 DECISIONS.md 5번에 기록했다." ← 검증·개선
```

### 골격 3 — 확인하지 않은 것
```
"확인하지 않았다. 위험: ___. 확인하려면 ___(명령·테스트·담당자 확인)."
```
추측으로 채우지 않는다. 아는 척보다 "확인하지 않음 + 위험 + 확인 방법"이 낫다.

금지: 근거 없는 "테스트했다" / AI·시간 탓 / 기록과 다른 숫자. 산출물과 어긋나는 내용, 일반론, AI 말투는 뺀다. 파일명·함수명·테스트명·숫자를 넣고 내 말투로 쓴다.

## 표 4개 (정리 항목보다 먼저 채운다)

### 오해하기 쉬운 지점 (겉보기와 실제 구현이 다른 곳)
겉보기나 흔한 가정이 실제 구현과 다르면, 가정에 맞춰 설명하지 않고 실제 구현을 먼저 적는다.
| 겉보기·흔한 가정 | 실제 구현 | 좌표 | 그렇게 한 이유 |
|---|---|---|---|
| 예: README "기준 초과면 알람" | 같은 값도 알람(`>=`) | `rules.py:42` · `test_threshold_equal_included` | 담당자 답변 3 |

### 부분별 설계 이유 (핵심 코드 지점마다 1행 · 8~15행)
대상: 진입점, 규칙 함수 각각, 임계값·상수, 정렬·tie-break, 제외·필터, 대체값 처리, 출력 쓰기, (웹) 요청 검증·응답에서 뺀 필드.
| 코드 위치(파일:줄·함수) | 무엇을 | 왜 이렇게 | 버린 대안과 이유 | 틀리면 생기는 일 | 근거(테스트·기록) |
|---|---|---|---|---|---|
|  |  |  |  |  |  |

### 장애 대응표 (상황마다 1행 · 지금 코드가 실제로 하는 일만)
| 상황 | 지금 코드가 하는 일(좌표) | 사람이 아는 방법(메시지·상태 열·로그) | 대응 | 다음 검증 |
|---|---|---|---|---|
|  |  |  |  |  |

기본 행(전부 쓴다, 해당 없으면 "해당 없음 — 이유"): 입력 파일 없음·빈 파일 / 열 이름·구분자·날짜 형식 변경 / 결측·표시용 값(-9999 등)·순간 튀는 값 / 중복·순서 뒤섞임 / 기준 데이터(마스터)와 불일치 / 데이터 10배 / 외부 입력(모델 응답 파일 등) 없음·형식 오류 / 출력 쓰기 실패 / (웹) 서버 다운·느림·잘못된 요청·큰 본문 / 담당자가 "이 숫자 틀렸다"고 할 때.

### 대체값·추정값·제외 (실제 결과와 구분)
| 어디서(좌표) | 무엇을 무엇으로(대체/추정/제외) | 건수 | 표시 방법(플래그·사유 열) | 결론에 주는 영향 |
|---|---|---|---|---|
|  |  |  |  |  |

## 정리 항목 (관점별 · 전부 채운다 · 해당 없으면 "해당 없음 — 이유" 한 줄)

### A. 개요
1. 한 문장 목표, 결과물의 사용자, 그 사용자가 바꾸는 결정
2. 실행 명령 한 줄과 입력 → 출력 흐름(파일 이름·행 수)
3. 작동 원리 3줄: 입력 → 규칙 → 출력, 전문 용어 없이
4. 제출물 목록과 파일별 역할(README 가 정한 이름·형식 그대로인지)
5. 성공 기준을 숫자로, 현재 값

### B. 의도 — 목표·제약
6. 반드시 지킬 조건과 조정 가능한 조건의 구분, 섞으면 생기는 문제
7. 상충 조건과 어느 쪽을 택했는지, 그 이유
8. README 에 없어 가정한 것과 틀리면 깨지는 것
9. 하지 않기로 한 것과 이유

### C. 담당자 합의·결정
10. 담당자에게 물은 것과 답이 설계를 바꾼 곳(질문 번호 → 바뀐 코드 위치)
11. 합의문 내용과 확인 시각(DECISIONS 0번)
12. 사람이 고른 결정 전부(`decisions/answers.md` 의 D번호 · 고른 후보 · 이유 · 담당자 답)
13. 담당자 답이 없거나 애매했던 곳과 처리 방법

### D. AI 활용 — Codex 위임과 검증
14. Codex 에 맡긴 것과 직접 한 것의 경계, 그렇게 나눈 이유
15. 목표·제약을 전달한 주요 위임 3개의 요지(목표·범위·금지·완료 조건)와 효과
16. Codex 출력을 믿지 않은 지점과 검증 방법
17. Codex 가 틀린 사례 하나와 발견·수정 과정(RED → FIX 기록, DECISIONS 4번)
18. 사용한 도구 설정: Codex 프로필·승인 모드·쓴 스킬·두 세션 운영
19. 토큰·시간을 아끼려고 한 것
20. 저장하지 않기로 한 데이터 또는 출력에서 뺀 열과 이유
21. 모델(또는 담당자 AI)이 준 값이 없거나 틀렸을 때 시스템이 하는 일

### E. 기술 — 구조·흐름·보안
22. 코드 구조: 파일별 역할, 순수 함수(`solve`)와 입출력 분리
23. 같은 입력에 같은 출력을 보장하는 방법(정렬·tie-break·반올림)
24. 결측·중복·경계값·시간대 처리와 코드 위치
25. 예외·실패 시 동작과 사용자가 아는 방법(장애 대응표에서 가장 위험한 2행 요약)
26. 비밀정보·개인정보 처리, 화면·출력에서 뺀 내부 필드
27. 데이터가 10배일 때 먼저 무너지는 곳
28. 더 단순한 대안을 쓰지 않은 이유

### F. 단계별 구현 (PLAN 4번 단계마다)
29. 단계 블록: 역할 1줄 · 작동 원리 3줄 · 구현 위치(파일:줄·함수) · 왜 이 방법(한 줄) · 결과 숫자(출처) · 테스트 이름 · 상태
30. 규칙표 전체: 규칙마다 발동 건수 · 테스트 · 상태(PLAN 4번)
31. 합계 보존: 입력 건수 = 통과 + 제외(사유별) 숫자와 확인 방법
32. 단계 보고서(`out/report/stage_*.html`)에서 확인한 것과 고친 것

### G. 검증·인지
33. 테스트 구성과 결과(정상·업무 규칙·경계값·실패 경로·계약이 각각 몇 개)
34. 먼저 FAIL 을 본 테스트와 그때 실패 내용
35. 검증 실행 기록: 명령·시각·결과(`green.txt`·DECISIONS 6번), 눈으로만 확인한 것과 그 이유
36. 핵심 숫자를 다른 방법으로 다시 계산한 결과
37. 사람이 직접 확인한 것(HUMAN_CHECK)과 결과
38. 담당자가 "이 숫자는 틀렸다"고 할 때 확인 순서
39. 가장 약한 부분과 틀리는 입력 하나(골격 2)
40. 설명하기 어려웠던 코드 줄과 쉬운 말 설명
41. 1차 동결 이후 바뀐 것(`preflight.py --check-freeze` 결과)

### H. 한계·다음 할 일
42. 못 한 것과 이유(TASK 8번)
43. 시간이 2배면 할 일, 다시 한다면 다르게 할 것
44. 실무에 넣는다면 먼저 확인할 것과 첫 운영 실험(샘플 대조·shadow·A/B), 측정할 것
45. 지표가 실제 업무 목표와 이어지는 방식
46. 규칙 사전을 나눴다면(입력 필터용·출력 검사용) 그 이유와 합치면 깨지는 것

## 핵심 3개 (정리 맨 위에 둔다)
① 상충 조건: "이 과제의 상충 조건은 ___와 ___였고, ___를 반드시 지킬 조건으로, ___를 조정 가능 조건으로 두었다. 섞으면 결과를 설명할 수 없기 때문이다."
② 가장 위험한 실패: "___ 입력에서 틀린다. 그러면 ___가 틀어진다. DECISIONS.md 5번에 적었고, 고치려면 ___가 필요하다."
③ Codex 를 믿지 않은 지점: "___는 맡겼고 ___는 직접 했다. 특히 ___는 ___로 다시 검증했다. 검증 없이 통과시키면 ___ 문제가 생기기 때문이다."

## 예시
**부분별 설계 이유 1행**
| 코드 위치 | 무엇을 | 왜 이렇게 | 버린 대안과 이유 | 틀리면 생기는 일 | 근거 |
|---|---|---|---|---|---|
| `clean.py:31 mark_missing()` | 온도 -9999 를 결측으로 표시 | 장비가 값 없음을 -9999 로 기록(담당자 답변 2) | 0 으로 대체 — 평균이 내려가 정상 설비가 이상으로 보임 | 평균 왜곡으로 보고서 결론이 틀어짐 | `test_sentinel_marked_missing` · 결측 37행(verify.json) |

**약점형 정리 (항목 39 · 약 400자)**
"-9999 는 결측으로 보고 평균에서 뺐고, `is_missing` 플래그와 결측 행 수(37행)를 출력에 남겼다(`clean.py:31`, `test_sentinel_marked_missing`). 약점은 -9999 가 아닌 순간 튀는 값은 걸러지지 않는다는 것이다. 이런 값이 섞이면 평균이 왜곡되고, 담당자가 보고서를 보고 정상 설비를 점검 대상으로 잘못 고를 수 있다. 다음에는 정상 범위를 담당자에게 확인하고, 범위 밖 값 테스트를 추가하겠다. 지금은 DECISIONS.md 5번에 적어 두었다."

## 용어 → 내 말 (정리에는 오른쪽 말로 쓴다)
| 용어 | 내 말로 |
|---|---|
| hard constraint / 위생 요건 | **빼는 것.** 후보에서 아예 제외한다 |
| soft ranking / 점수 | **줄 세우는 것.** 순서만 정한다, 빠지지는 않는다 |
| tie-break | 점수가 같을 때 누가 먼저 나올지 정한 규칙 |
| 결정론적 / 재현성 | 두 번 돌려도 같다 |
| 견고성 / robustness | 이상한 게 들어와도 안 터진다 |
| fallback | 원래 방법이 안 될 때 쓰는 대비책, 썼다는 표시를 남긴다 |
| 경계값 / edge case | 딱 걸치는 값(임계값과 같음, ±1) |
| sentinel / 표시용 값 | "값 없음"을 뜻하려고 넣은 가짜 숫자(-9999 등) |
| leakage / 누수 | 아직 안 일어난 미래 정보를 몰래 쓰는 것 |
| 멱등성 | 같은 걸 두 번 받아도 한 번만 반영 |
| 가드레일 | 절대 나가면 안 되는 결과를 코드로 막은 것 |
| TDD / 먼저 FAIL | 확인할 문장을 먼저 정하고, 안 되는 걸 보고, 되게 만든다 |

## 코드 조각 카드 (기능 하나 끝날 때마다 1장, DECISIONS 1번 옆에)
```
코드: <5~10줄>
내 설명(3줄, 전문 용어 없이):
여기서 내가 정한 것: <가정과 틀리면 깨지는 것>
```

## 제약의 대가 (규칙을 따르느라 잃은 것)
"담당자 규칙 ___를 그대로 따르면 ___를 잃는다(크기: ___). 실무라면 ___ 또는 ___가 대안이다. 그래도 따른 이유는 명시된 규칙이고 채점 기준이 그 규칙일 때 임의 변경이 전부 틀리기 때문이다. 대가는 DECISIONS.md 5번에 적었다." — "시키는 대로 했다"와 "대가를 알고 시키는 대로 했다"는 다르다.

# 최종 구현 종합정리 (작업 마무리 · 모든 문장에 증거 좌표)

무엇을 왜 어떻게 만들었고, 어떻게 검증했고, 어디서 틀릴 수 있는지를 한 문서로 모은다. 동결 구간(144분~)에 보고서 세션에서 `$implementation-summary` 가 아래 **정리 항목 전부**를 채워 `out/report/implementation_summary.md` 로 낸다. 정리 관점은 넷이다: 의도(목표·제약) · AI 활용(위임·검증) · 기술(실행·구조·보안) · 인지(검증·한계·설명). 정리한 내용과 실제 구현이 다르면 구현을 기준으로 고친다.

## 문서 모양
```
# 최종 구현 종합정리 — <과제 이름>
한 문장: (TASK.md 한 문장 그대로)
## 핵심 3개                          ← 맨 위
## A. 개요 … ## H. 한계·다음 할 일     ← 아래 항목 번호 그대로, 빠짐없이
## 설명이 막힌 항목
## 근거 없음 목록                     ← 기록에서 숫자·좌표를 못 찾은 항목
```

## 골격 1 — 결정형 (사실 → 결정 → 근거 → 한계)
```
사실  "README·담당자는 X라고만 정했다."
결정  "그래서 Y로 정했다. 대안 Z는 ~ 때문에 버렸다."
근거  "근거는 ~이고, test_xxx 3개와 preflight로 확인했다."
한계  "W인 입력에서는 틀릴 수 있어 DECISIONS.md 5번에 적었다."
```
금지: 모르는 것을 아는 척 / 근거 없는 "테스트했다" / AI·시간 탓. 대신 "확인하지 않았다. 확인하려면 A를 보면 된다."

## 골격 2 — 약점형 (지목 → 파급 → 계획)
위험·장애·가장 약한 곳을 정리하는 항목은 세 단계로 쓴다.
```
지목  "약점은 <파일>의 <함수/규칙>이 <조건> 입력을 처리하는 방식이다."          ← 구체적 좌표
파급  "이 경우 <결과물>이 <어떻게> 틀리고, <누가> <어떤 결정>을 잘못하게 된다."  ← 왜 위험한가
계획  "<테스트/확인>으로 검증하고 <수정>한다. 지금은 DECISIONS.md 5번에 기록했다." ← 검증·개선
```
주의: 산출물과 어긋나는 내용, 일반론, AI 말투는 뺀다. 파일명·함수명·테스트명·숫자를 넣고 내 말투로 쓴다.

## 용어 → 내 말 (정리에는 오른쪽 말로 쓴다)
| 용어 | 내 말로 |
|---|---|
| hard constraint / 위생 요건 | **빼는 것.** 후보에서 아예 제외한다 |
| soft ranking / 점수 | **줄 세우는 것.** 순서만 정한다, 빠지지는 않는다 |
| tie-break | 점수가 같을 때 누가 먼저 나올지 정한 규칙 |
| 결정론적 / 재현성 | 두 번 돌려도 같다 |
| 견고성 / robustness | 이상한 게 들어와도 안 터진다 |
| fallback | 원래 방법이 안 될 때 쓰는 대비책, 썼다는 표시를 남긴다 |
| 경계값 / edge case | 딱 걸치는 값(임계값과 같음, ±1) |
| leakage / 누수 | 아직 안 일어난 미래 정보를 몰래 쓰는 것 |
| 멱등성 | 같은 걸 두 번 받아도 한 번만 반영 |
| 가드레일 | 절대 나가면 안 되는 결과를 코드로 막은 것 |
| TDD / 먼저 FAIL | 확인할 문장을 먼저 정하고, 안 되는 걸 보고, 되게 만든다 |

## 코드 조각 카드 (기능 하나 끝날 때마다 1장, DECISIONS 1번 옆에)
```
코드: <5~10줄>
내 설명(3줄, 전문 용어 없이):
여기서 내가 정한 것: <가정과 틀리면 깨지는 것>
```

## 제약의 대가 (규칙을 따르느라 잃은 것)
"담당자 규칙 ___를 그대로 따르면 ___를 잃는다(크기: ___). 실무라면 ___ 또는 ___가 대안이다. 그래도 따른 이유는 명시된 규칙이고 채점 기준이 그 규칙일 때 임의 변경이 전부 틀리기 때문이다. 대가는 DECISIONS.md 5번에 적었다." — "시키는 대로 했다"와 "대가를 알고 시키는 대로 했다"는 다르다.

## 설명이 막힌 항목 (심사자 시뮬레이션 후 누적 · 막힌 곳 = 문서의 구멍)
| 항목 | 그때 설명 | 다시 정리한 내용 | 문서에 추가한 곳 |
|---|---|---|---|
|  |  |  |  |

## 정리 항목 (관점별 · 전부 채운다 · 해당 없으면 "해당 없음 — 이유" 한 줄)

### A. 개요
1. 한 문장 목표, 결과물의 사용자, 그 사용자가 바꾸는 결정
2. 실행 명령 한 줄과 입력 → 출력 흐름(파일 이름·행 수)
3. 제출물 목록과 파일별 역할(README 가 정한 이름·형식 그대로인지)
4. 성공 기준을 숫자로, 현재 값

### B. 의도 — 목표·제약
5. 반드시 지킬 조건과 조정 가능한 조건의 구분, 섞으면 생기는 문제
6. 상충 조건과 어느 쪽을 택했는지, 그 이유
7. README 에 없어 가정한 것과 틀리면 깨지는 것
8. 하지 않기로 한 것과 이유

### C. 담당자 합의·결정
9. 담당자에게 물은 것과 답이 설계를 바꾼 곳(질문 번호 → 바뀐 코드 위치)
10. 합의문 내용과 확인 시각(DECISIONS 0번)
11. 사람이 고른 결정 전부(`decisions/answers.md` 의 D번호 · 고른 후보 · 이유 · 담당자 답)
12. 담당자 답이 없거나 애매했던 곳과 처리 방법

### D. AI 활용 — Codex 위임과 검증
13. Codex 에 맡긴 것과 직접 한 것의 경계, 그렇게 나눈 이유
14. Codex 출력을 믿지 않은 지점과 검증 방법
15. 위임 프롬프트에 넣은 제약(범위·금지·완료 조건)과 효과
16. Codex 가 틀린 사례 하나와 발견·수정 과정
17. 토큰·시간을 아끼려고 한 것(두 세션 운영, 스킬 정리, 출력 줄이기 등)
18. 저장하지 않기로 한 데이터 또는 출력에서 뺀 열과 이유
19. 모델(또는 담당자 AI)이 준 값이 없거나 틀렸을 때 시스템이 하는 일

### E. 기술 — 구조·흐름·보안
20. 코드 구조: 파일별 역할, 순수 함수(`solve`)와 입출력 분리
21. 같은 입력에 같은 출력을 보장하는 방법(정렬·tie-break·반올림)
22. 결측·중복·경계값·시간대 처리와 코드 위치
23. 예외·실패 시 동작과 사용자가 그것을 아는 방법
24. 비밀정보·개인정보 처리, 화면·출력에서 뺀 내부 필드
25. 입력 형식(열 이름·구분자·날짜 형식)이 바뀔 때의 동작과 사용자가 아는 방법
26. 데이터가 10배일 때 먼저 무너지는 곳
27. 서버·화면이 죽거나 느려질 때 지금 코드가 하는 일
28. 더 단순한 대안을 쓰지 않은 이유

### F. 단계별 구현 (PLAN 4번 단계마다)
29. 단계 블록: 역할 1줄 · 구현 위치(파일:줄·함수) · 방법 3~5줄 · 결과 숫자(출처) · 테스트 이름 · 상태
30. 규칙표 전체: 규칙마다 발동 건수 · 테스트 · 상태(PLAN 4번)
31. 합계 보존: 입력 건수 = 통과 + 제외(사유별) 숫자와 확인 방법
32. 단계 보고서(`out/report/stage_*.html`)에서 확인한 것과 고친 것

### G. 검증·인지
33. 테스트 구성과 결과(정상·업무 규칙·경계값·실패 경로·계약이 각각 몇 개)
34. 먼저 FAIL 을 본 테스트와 그때 실패 내용
35. 핵심 숫자를 다른 방법으로 다시 계산한 결과
36. 사람이 직접 확인한 것(HUMAN_CHECK)과 결과
37. 담당자가 "이 숫자는 틀렸다"고 할 때 확인 순서
38. 가장 약한 부분과 틀리는 입력 하나(골격 2)
39. 설명하기 어려웠던 코드 줄과 쉬운 말 설명
40. 1차 동결 이후 바뀐 것(`preflight.py --check-freeze` 결과)

### H. 한계·다음 할 일
41. 못 한 것과 이유(TASK 8번)
42. 시간이 2배면 할 일, 다시 한다면 다르게 할 것
43. 실무에 넣는다면 먼저 확인할 것과 첫 운영 실험(샘플 대조·shadow·A/B), 측정할 것
44. 지표가 실제 업무 목표와 이어지는 방식
45. 규칙 사전을 나눴다면(입력 필터용·출력 검사용) 그 이유와 합치면 깨지는 것

## 핵심 3개 (정리 맨 위에 둔다)
① 상충 조건: "이 과제의 상충 조건은 ___와 ___였고, ___를 반드시 지킬 조건으로, ___를 조정 가능 조건으로 두었다. 섞으면 결과를 설명할 수 없기 때문이다."
② 가장 위험한 실패: "___ 입력에서 틀린다. 이유는 ___이고 DECISIONS.md 5번에 적었다. 고치려면 ___가 필요하지만 시간 안에 안 된다고 판단했다."
③ Codex 를 믿지 않은 지점: "___는 맡겼고 ___는 직접 했다. 특히 ___는 ___로 다시 검증했다. 검증 없이 통과시키면 ___ 문제가 생기기 때문이다."

## 예시 정리 (항목 38 · 약 500자)
"README에는 '임계값 초과 시 알람'이라고만 쓰여 있었고, 담당자는 '기준값과 같으면 포함'이라고 답했다. 그래서 비교를 `>=`로 구현하고 test_threshold_equal_included 테스트로 고정했다. 가장 약한 부분은 센서값이 비어 있는 행이다. 결측을 '판정 불가'로 분류해 알람에서 제외하고 별도 열에 표시했는데, 담당자가 결측을 이상으로 간주한다면 누락이 생긴다. 이 가정은 DECISIONS.md 2번에 적었고, 결측 행 수(37행)를 리포트에 명시했다. 시간이 더 있었다면 결측 행을 담당자와 샘플로 확인했을 것이다."

# 후속 서술형 대비 (6문항 × 5분 · AI·복사·붙여넣기 금지 · 직접 타이핑)

문항은 **내 제출물과 작업 기록에서 생성**된다. 평가 축은 기술(실행·구조·보안)·의도(목표·제약 전달)·인지(검증·수정·설명). "질문의 전제와 실제 구현이 다르면 차이를 밝히고 본인의 작업을 설명"(공식 안내).

## 5분 운용
| 시간 | 할 일 |
|---|---|
| 0:00–0:40 | 질문 두 번 읽기. 묻는 축(의도/기술/인지) 판단. 전제가 내 구현과 다르면 첫 문장에서 바로잡기 |
| 0:40–3:40 | 4문장 골격으로 작성(400~600자): **사실 → 결정 → 근거 → 한계** |
| 3:40–4:40 | 숫자·파일명·테스트 이름 확인, 과장 삭제 |
| 4:40 | 제출 (시간 종료 시 자동 확정) |

## 답변 골격
```
사실  "문제(README/담당자)에는 X라고만 정해져 있었습니다."
결정  "그래서 저는 Y로 정했습니다. (대안 Z는 ~ 때문에 버렸습니다.)"
근거  "근거는 ~이고, test_xxx 3개와 preflight로 확인했습니다."     ← 점수
한계  "다만 W인 입력에서는 틀릴 수 있어 DECISIONS.md에 적어 두었습니다." ← 신뢰
```
금지: 모르는 것을 아는 척 / 근거 없는 "테스트했습니다" / AI·시간 탓. 대신 "확인하지 않았습니다. 확인하려면 A를 보면 됩니다."

## 두 번째 골격 — 약점·장애 질문 (공개 후기의 모범답안 구조)
"장애가 발생하면 어떻게 대응하나", "가장 약한 부분은"처럼 리스크를 묻는 문항은 세 단계로 쓴다.
```
지목  "약점은 <파일>의 <함수/규칙>이 <조건> 입력을 처리하는 방식입니다."     ← 구체적 좌표
파급  "이 경우 <결과물>이 <어떻게> 틀리고, <누가> <어떤 결정>을 잘못하게 됩니다." ← 왜 위험한가
계획  "다음에는 <테스트/확인> 으로 검증하고 <수정> 하겠습니다. 지금은 DECISIONS.md 5번에 기록했습니다." ← 검증·개선
```
재심문 주의: 산출물과 어긋나는 답, 일반론, AI 말투는 재질문을 부른다. 파일명·함수명·테스트명·숫자를 넣고 내 말투로 쓴다.


## 심사자 용어 → 내 말 (들으면 번역해서 이해하고, 답은 오른쪽으로)
| 들리는 말 | 내 말로 |
|---|---|
| hard constraint / 위생 요건 | **빼는 것.** 후보에서 아예 제외한다 |
| soft ranking / 점수 | **줄 세우는 것.** 순서만 정한다, 빠지지는 않는다 |
| tie-break | 점수가 같을 때 누가 먼저 나올지 정한 규칙 |
| 결정론적 / 재현성 | 두 번 돌려도 같다 |
| 견고성 / robustness | 이상한 게 들어와도 안 터진다 |
| fallback | 원래 방법이 안 될 때 쓰는 대비책, 썼다는 표시를 남긴다 |
| 경계값 / edge case | 딱 걸치는 값(임계값과 같음, ±1) |
| leakage / 누수 | 아직 안 일어난 미래 정보를 몰래 쓰는 것 |
| 멱등성 | 같은 걸 두 번 받아도 한 번만 반영 |
| 가드레일 | 절대 나가면 안 되는 결과를 코드로 막은 것 |
| TDD / 먼저 FAIL | 확인할 문장을 먼저 정하고, 안 되는 걸 보고, 되게 만든다 |

## 코드 조각 카드 (기능 하나 끝날 때마다 1장, DECISIONS 1번 옆에)
```
코드: <5~10줄>
내 설명(3줄, 전문 용어 없이):
여기서 내가 정한 것: <가정과 틀리면 깨지는 것>
```

## 제약의 대가 (함정 질문 "그 규칙 때문에 품질이 떨어지지 않나요?")
"담당자 규칙 ___를 그대로 따르면 ___를 잃습니다(크기: ___). 실무라면 ___ 또는 ___가 대안입니다. 그래도 따른 이유는 명시된 규칙이고 채점 기준이 그 규칙일 때 임의 변경이 전부 틀리기 때문입니다. 대가는 DECISIONS.md 5번에 적었습니다." — "시키는 대로 했다"와 "대가를 알고 시키는 대로 했다"는 다르다.

## 질문뱅크 (축별)

### 의도 — 목표·제약을 어떻게 정했나
1. 이 결과물의 사용자는 누구이고 어떤 결정을 바꾸나?
2. 반드시 지킬 조건과 조정 가능한 조건을 어떻게 나눴나?
3. README에 없는 것 중 무엇을 가정했나? 틀리면 무엇이 깨지나?
4. 담당자에게 무엇을 물었고 답이 설계를 어떻게 바꿨나?
5. 하지 않기로 한 것과 이유는?
6. 성공 기준을 숫자로 말하면? 현재 값은?

### AI 활용 — Codex에 무엇을 맡겼나
7. Codex에 맡긴 것과 직접 한 것의 경계는? 왜 그렇게 나눴나?
8. Codex 출력을 신뢰하지 않은 지점과 검증 방법은?
9. 프롬프트에 어떤 제약(범위·금지·완료 조건)을 넣었나? 효과가 있었나?
10. Codex가 틀린 사례 하나와 어떻게 발견·수정했나?
11. 토큰·시간을 아끼기 위해 무엇을 했나?
11-1. 저장하지 않기로 한 데이터(또는 출력에서 뺀 열)는 무엇이고 왜인가?
11-2. 모델(또는 담당자 AI)이 준 값이 없거나 틀렸을 때 시스템은 무엇을 하나?

### 기술 — 실행·구조·보안
12. 실행 명령 한 줄과 입력→출력 흐름은?
13. 같은 입력에 같은 출력을 보장하는 방법(정렬·tie-break·반올림)은?
14. 결측·중복·경계값·시간대를 어떻게 처리했나? 코드 어디에 있나?
15. 예외·실패 시 동작과 사용자가 그것을 아는 방법은?
16. 비밀정보·개인정보 처리 방식은?
17. 더 단순한 대안은 왜 부족했나?
18. 데이터가 10배면 어디가 먼저 무너지나?
18-1. 입력 파일 형식(열 이름·구분자·날짜 형식)이 바뀌면 프로그램은 어떻게 되나? 사용자는 어떻게 아나?
18-2. 서비스(서버)가 죽거나 응답이 느려지면 어떻게 대응하나? 지금 코드는 무엇을 하나?
18-3. 담당자가 "이 숫자는 틀렸다"고 하면 어디부터 확인하나?

### 검증·인지 — 가장 낮게 나오는 축
19. 가장 약한 부분은? 어떤 입력에서 틀리나(구체적으로 하나)?
20. 테스트가 실패하는 것을 본 적이 있나? 어떤 테스트였나?
21. 설명 못 하는 코드 줄이 있나?
22. 핵심 숫자를 다른 방법으로 재계산했나? 결과는?
23. 다시 한다면 무엇을 다르게 하겠나? 시간이 2배면?
24. 이 지표가 실제 업무 목표와 어떻게 연결되나? 내일 실무에 넣는다면 먼저 확인할 것은?
25. 첫 운영 실험(A/B·shadow·샘플 대조)을 설계한다면? 무엇을 측정하나?
26. 규칙 사전을 둘(입력 필터용·출력 검사용)로 나눴다면 왜인가? 합치면 무엇이 깨지나?

## 제출 확정 전 반드시 써 둘 답변 3개 (머릿속 고정)
① 상충 조건: "이 문제의 상충 조건은 ___와 ___였고, ___를 반드시 지킬 조건으로, ___를 조정 가능 조건으로 두었습니다. 섞으면 결과를 설명할 수 없기 때문입니다."
② 가장 위험한 실패: "___ 입력에서 틀립니다. 이유는 ___이고 DECISIONS.md 5번에 적었습니다. 고치려면 ___가 필요하지만 시간 안에 안 된다고 판단했습니다."
③ Codex를 믿지 않은 지점: "___는 맡겼고 ___는 직접 했습니다. 특히 ___는 ___로 다시 검증했습니다. 검증 없이 통과시키면 ___ 문제가 생기기 때문입니다."

## 예시 답변 (질문 19 · 약 500자)
"README에는 '임계값 초과 시 알람'이라고만 쓰여 있었고, 담당자는 '기준값과 같으면 포함'이라고 답했습니다. 그래서 비교를 `>=`로 구현하고 test_threshold_equal_included 테스트로 고정했습니다. 가장 약한 부분은 센서값이 비어 있는 행입니다. 저는 결측을 '판정 불가'로 분류해 알람에서 제외하고 별도 열에 표시했는데, 담당자가 결측을 이상으로 간주한다면 누락이 생깁니다. 이 가정은 DECISIONS.md 2번에 적었고, 결측 행 수(37행)를 리포트에 명시했습니다. 시간이 더 있었다면 결측 행을 담당자와 샘플로 확인했을 것입니다."

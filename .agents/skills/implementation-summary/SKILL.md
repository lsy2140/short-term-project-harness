# implementation-summary

목표: 처음 보는 사람이 코드를 열지 않고도 **이 과제에서 무엇을 왜 어떻게 만들었고, 어떻게 검증했고, 장애가 나면 어떻게 되는지** 알 수 있는 최종 구현 종합정리를 만든다. 문장마다 코드 위치나 실행 기록으로 확인할 수 있어야 하고, 사람이 자기 말로 설명할 수 있는 문장만 남긴다.

## 범위
- 쓰는 곳: `out/report/implementation_summary.md` 한 파일. 코드·`tests/`·TASK/PLAN/DECISIONS·`decisions/`·`out/debug/` 는 **읽기만**.
- 실행: 읽기 명령(`head`·`wc -l`·`grep`·`sed -n`)만. 테스트·앱·서버 실행 금지 — 숫자는 기록에서 옮긴다.
- 메인 세션이 동결 문서를 고치는 동안 보고서 세션에서 돌린다(AGENTS.md 4절).

## 절차
1. **읽기**: `TASK.md`(사실·가정·안 할 일·완료 조건·못 한 것), `DECISIONS.md`(0 합의문·1 결정·2 데이터 처리·3 맡긴 것·4 오류 수정·5 한계·6 검증 로그), `decisions/answers.md`, `PLAN.md` 4번 규칙표, `out/debug/NN_*/note.md`(왜)·`verify.json`·`green.txt`·`red.txt`, `out/report/stage_*.json`(있으면). 코드는 `grep -n "def \|# 결정:"` 과 `sed -n a,bp` 로 위치만 본다(파일 통째 금지).
2. **표 4개 먼저**(지침의 '표 4개'): 오해하기 쉬운 지점 → 부분별 설계 이유(핵심 코드 지점 8~15행: 진입점·규칙 함수·임계값·정렬·제외·대체값·출력·웹 요청 검증) → 장애 대응표(기본 행 전부, 해당 없으면 이유) → 대체값·추정값·제외(건수·표시 방법·결론에 주는 영향).
3. **정리 항목 전부**: A~H 를 번호 순서대로 모두 채운다. 개수를 줄이지 않는다. 해당 없는 항목은 지우지 말고 "해당 없음 — 이유" 한 줄.
4. **골격**: 결정은 4문장(사실 → 결정 → 근거 → 한계), 위험·장애·약한 곳은 3단(지목 → 파급 → 계획), 확인 못 한 것은 "확인하지 않았다. 위험: ___. 확인하려면 ___". 제약이 결정을 바꾼 곳에는 **제약의 대가** 한 줄.
5. **대조**: 적은 코드 좌표는 전부 `sed -n 'N,Mp' <파일>` 로 다시 열어 문장과 맞는지 확인한다. 숫자는 기록(verify.json·green.txt·출력 metadata)과 맞춘다. 안 맞으면 기록과 코드를 기준으로 문장을 고친다. 기록에 없으면 골격 3으로 쓰고 맨 아래 '근거 없음 목록'에 올린다.
6. **맨 위**: 한 문장 요약 + **핵심 3개**(상충 조건 / 가장 위험한 실패 / Codex 를 믿지 않은 지점).
7. **쉬운 말**: 사람이 자기 말로 설명하기 어려운 문장(전문 용어·긴 문장)은 `[다시 쓰기]` 로 표시하고 쉬운 말로 다시 쓴다. 설명 못 하는 문장은 남기지 않는다.
8. **보고 5줄**: 파일 경로 / 채운 항목 수·해당 없음 수·표별 행 수 / 핵심 3개 제목 / 근거 없음 목록 / 사람이 먼저 볼 곳(오해하기 쉬운 지점·장애 대응표의 위험한 행).

## 금지
- 제출물에 없는 기능·검증을 있는 것처럼 쓰기, 추정 숫자, 대조하지 않은 코드 좌표, 메인 세션 파일 수정, 테스트·서버 실행, 항목이나 표 행을 골라서 일부만 정리하기.

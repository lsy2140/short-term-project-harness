# implementation-summary

목표: 처음 보는 사람이 코드를 열지 않고도 **이 과제에서 무엇을 왜 어떻게 만들었고, 어떻게 검증했고, 어디서 틀릴 수 있는지** 알 수 있는 최종 구현 종합정리를 만든다. 사람이 자기 말로 설명할 수 있는 문장만 남긴다.

## 범위
- 쓰는 곳: `out/report/implementation_summary.md` 한 파일. 코드·`tests/`·TASK/PLAN/DECISIONS·`decisions/`·`out/debug/` 는 **읽기만**.
- 실행: 읽기 명령(`head`·`wc -l`·`grep`·`sed -n`)만. 테스트·앱·서버 실행 금지 — 숫자는 기록에서 옮긴다.
- 메인 세션이 동결 문서를 고치는 동안 보고서 세션에서 돌린다(AGENTS.md 4절).

## 절차
1. **읽기**: `TASK.md`(사실·가정·안 할 일·완료 조건·못 한 것), `DECISIONS.md`(0 합의문·1 결정·4 Codex 를 믿지 않은 것·5 깨질 입력·6 검증 로그), `decisions/answers.md`, `PLAN.md` 4번 규칙표, `out/debug/NN_*/verify.json`·`note.md`·`green.txt`, `out/report/stage_*.json`(있으면). 코드는 `grep -n "def \|# 결정:"` 과 `sed -n a,bp` 로 위치만 본다(파일 통째 금지).
2. **정리 항목 전부**: `docs/implementation_summary.md` 의 A~H 항목을 번호 순서대로 모두 채운다. 개수를 줄이지 않는다. 해당 없는 항목은 지우지 말고 "해당 없음 — 이유" 한 줄.
3. **골격**: 결정을 정리하는 항목은 4문장(사실 → 결정 → 근거 → 한계), 위험·장애·약한 곳은 3단(지목 → 파급 → 계획). 제약(표준 라이브러리·시간·데이터)이 결정을 바꾼 항목에는 **제약의 대가**(무엇을 잃나·크기, 실무 대안 2개, 그래도 따른 이유)를 한 줄 덧붙인다.
4. **단계별 구현(F)**: PLAN 4번 단계마다 1블록 — 역할 1줄 · 구현 위치(파일:줄·함수) · 방법 3~5줄 · 결과 숫자(출처) · 테스트 이름 · 상태.
5. **숫자·좌표**: 기록에 있는 실제 값만(테스트 수·행 수·경계값·발동 건수). 기록에 없으면 "확인하지 않음 — 확인하려면 ___" 으로 쓰고 맨 아래 '근거 없음 목록'에 올린다. 모든 문장 끝에 증거 좌표(파일:줄·테스트·명령).
6. **맨 위**: 한 문장 요약 + **핵심 3개**(상충 조건 / 가장 위험한 실패 / Codex 를 믿지 않은 지점).
7. **쉬운 말**: 사람이 자기 말로 설명하기 어려운 문장(전문 용어·긴 문장)은 `[다시 쓰기]` 로 표시하고 쉬운 말로 다시 쓴다. 설명 못 하는 문장은 남기지 않는다.
8. **보고 5줄**: 파일 경로 / 채운 항목 수·해당 없음 수 / 핵심 3개 제목 / 근거 없음 목록 / 사람이 직접 확인할 곳.

## 금지
- 제출물에 없는 기능·검증을 있는 것처럼 쓰기, 추정 숫자, 메인 세션 파일 수정, 테스트·서버 실행, 항목을 골라서 일부만 정리하기.

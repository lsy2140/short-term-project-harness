# unit-test-starter

목표: 규칙 1개 = 테스트 1개를 **표 → 승인 → 작성 → FAIL 확인 → 구현 → PASS** 순서로 만든다. 실패를 못 본 테스트는 믿지 않는다(AGENTS.md 3절).

## 절차
1. 대상 함수의 시그니처와 규칙 문장(TASK.md 5번 또는 DECISIONS.md 0번)을 인용한다. 규칙 문장이 없으면 먼저 묻는다. 규칙이 업무 결과를 바꾸는 선택(경계 포함 여부·자정·시간대·단위·제외·정렬·산식·보고 항목)이면 사람이 결정한 기록(`decisions/answers.md` 또는 pending.md 의 `[x]`)이 있는지 확인한다.
2. 케이스 표를 **먼저 제안**하고 승인을 기다린다. 표 위 첫 줄에 `업무 규칙: 없음` 또는 `업무 규칙: D03(결정됨)·D07(대기)` 를 적는다. 사람 결정이 없는 업무 규칙에 기대는 행은 표에 넣지 않고 pending.md 항목(`담당자 확인: 필요` + 담당자 질문)으로 먼저 올린다 — 표 승인은 업무 규칙 결정을 대신하지 않는다(AGENTS.md 5절). 최소 구성: 정상 2 · 경계 1(임계값과 같음 / ±1) · 결측 1(''·NA·-) · 중복 1. 규칙이 "거부"라면 `assertRaises(ValueError)` 케이스를 넣는다.
3. 승인되면 `tests/test_<모듈>.py`에 쓴다. `tests/test_template.py` 형식을 따르고, 케이스마다 `# 무엇을 시험하나:` 한 줄, 표의 값을 그대로 쓴다(임계값 상수는 코드에서 import).
4. `python3 -m unittest -v tests.test_<모듈>` 실행 → **FAIL/ERROR 출력을 보여준다**. 이미 PASS면 테스트가 규칙을 재지 않는 것이니 입력을 바꿔 다시 FAIL을 본다.
5. 구현 후 같은 명령으로 PASS를 보이고 이 단계의 디버그 폴더에 red.txt(FAIL 출력)·green.txt(PASS 출력)를 남긴다.

## 케이스 표 형식
| # | 유형 | 입력(3행 이내) | 기대 | 무엇을 시험하나 |
|---|---|---|---|---|

## 규칙
- 결정적: 랜덤·현재 시각·네트워크·파일 순서 의존 금지. 시각은 고정 문자열, 정렬·tie-break는 명시.
- 스냅샷·전체 출력 비교 대신 값·행 수·예외를 assert 한다.
- 입력은 표의 값을 코드 안에 둔다(`data/` 의존 금지). 큰 샘플이 필요하면 `scripts/make_edge_cases.py` 출력 경로를 쓴다.
- **기존 테스트를 고치거나 지워야 하면 먼저 말하고**(무엇을·왜·대신 무엇으로) 승인 뒤에 한다. 통과시키려고 assert를 약화하지 않는다.
- 기대값에 반올림·tie-break가 있으면 코드의 `# 결정:` 주석과 같은 값인지 확인하고, 다르면 테스트가 아니라 결정을 먼저 맞춘다.

## 금지
- 표 승인 전 파일 작성. 구현과 테스트를 같은 턴에 둘 다 쓰기. 테스트에 맞춘 하드코딩. 사람 결정 없이 업무 규칙(경계 포함 여부 등)을 기대값으로 고정하기.
